# pcf79xxprog

A single-file Arduino sketch for a **classic ESP32-WROOM** that controls the NXP PCF79xx Monitor and Download Interface (MDI) through a local web page.

The port follows the command set and memory operations in Tusker Tools' `PCF79xx_Tool`, but it does **not** copy the latest interrupt routine literally. The repository itself warns that the newest code stopped working for multiple users. This port therefore uses a small ESP32 edge-state machine based on the earlier target-clocked transfer sequence, while retaining the later tool's useful read, program, erase, protect, signature, and special-page functions.

> **Development status:** compile/syntax reviewed, but not yet validated against physical PCF hardware. Begin with read-only tests and a sacrificial target before erasing, programming, or protecting a valuable key.

## Files

- `pcf79xxprog.ino` — the complete firmware, webserver, web UI, MDI engine, and RAM buffers.
- `README.md` — wiring, power, timing, memory map, protocol notes, source findings, and test procedure.

No third-party Arduino libraries are required. The sketch uses `WiFi.h` and `WebServer.h` from the Espressif Arduino core.

## Direct answer: should the target be powered from ESP32 3.3 V?

**Use 3.3 V for both the PCF target supply and the MDI logic, but do not feed the target from an ESP32 GPIO.**

The ESP32 board's regulated 3.3 V rail can be used directly for initial bench testing when:

1. its regulator has enough spare current,
2. the coin cell is removed or electrically isolated, and
3. target and ESP32 grounds are connected.

Monitor-mode entry requires a repeatable power-off/power-on sequence. With direct wiring, perform that cycle manually by disconnecting and reconnecting target 3.3 V. For automatic power sequencing from the webserver, GPIO25 controls only the **enable/gate** of an optional switched 3.3 V rail; it must not power the target directly.

For a complete remote PCB, a current-limited bench supply or a dedicated 3.3 V regulator/load switch is safer than assuming the ESP32 board regulator has enough margin. A bare PCF IC consumes little, but a complete key board can include LEDs, button networks, capacitors, LF circuitry, and a UHF transmitter.

Never apply 5 V to MSDA or MSCL when using the ESP32. A generic BSS138 I²C level-shifter board is not recommended: MDI is not I²C, the PCF generates the clock, and MSDA is actively driven in both directions.

### Recommended target power circuit

```text
ESP32 board 3V3 ---- load switch IN
                       load switch OUT ---- PCF BAT/VCC
GPIO25 -------------- load switch EN
ESP32 GND -------------------------------- PCF GND
```

For a P-channel MOSFET high-side switch, change:

```cpp
static constexpr bool TARGET_POWER_ACTIVE_HIGH = false;
```

Add **100 nF** and approximately **1–4.7 µF** close to the target supply connection. A discharge resistor on the switched rail can improve repeatable power-down if the key PCB retains charge.

## Initial direct-power wiring

For the first bench tests, the sketch uses the ESP32's internal MSDA pull-up:

```cpp
pinMode(PIN_MSDA, INPUT_PULLUP);
```

Use this wiring:

```text
ESP32 3V3 → PCF VCC/BAT
ESP32 GND → PCF GND
GPIO26    → MSDA through 330 Ω–1 kΩ
GPIO27    ← MSCL through 330 Ω–1 kΩ
```

The values are ESP32 GPIO numbers, not Uno-style `D` labels. Remove or isolate the target coin cell before applying ESP32 power. GPIO27 is an input because MSCL is generated by the PCF target.

An external MSDA pull-up may be omitted initially. The internal ESP32 pull-up provides a defined high level whenever the firmware releases MSDA for target-to-programmer data. For a permanent fixture, long clip leads, or electrically noisy conditions, add **4.7 kΩ–10 kΩ from MSDA to the target's switched 3.3 V rail**. Connecting it to the switched rail avoids back-powering an unpowered target through MSDA.

## Optional software-controlled target power

The initial direct-power wiring requires manually disconnecting/reconnecting 3.3 V for a full target power cycle. To let the webserver perform that sequence automatically, use GPIO25 to control a load switch or P-channel MOSFET:

| ESP32-WROOM | Connection | Notes |
|---|---|---|
| GPIO25 | Target-power switch EN/gate | Control only; not the target supply |
| GPIO26 | MSDA | Bidirectional; 330 Ω–1 kΩ series resistor |
| GPIO27 | MSCL | PCF-generated clock; 330 Ω–1 kΩ series resistor |
| GND | Target GND | Mandatory common reference |
| Switched 3.3 V | PCF BAT/VCC | Coin cell removed or isolated |

The pins are near the top of the `.ino` and can be changed:

```cpp
static constexpr uint8_t PIN_TARGET_POWER = 25;
static constexpr uint8_t PIN_MSDA = 26;
static constexpr uint8_t PIN_MSCL = 27;
```

MSDA and MSCL must remain below GPIO32 in this version because the ISR uses the classic ESP32 low-bank direct GPIO registers.

### Before connecting a key PCB

- Remove or isolate the coin cell.
- Confirm the target BAT pad is not still tied to another power source.
- Confirm 3.3 V at the target with a meter before attaching MDI lines.
- Start with 1 kΩ series resistors on MSDA and MSCL.
- Verify the load switch turns fully off and the target rail discharges.
- Do not press remote buttons during MDI work.

## Why ESP32 is the MDI controller

The ESP32 should be the controller for this module even when the final project also contains an ATmega328P or ATmega2560.

- PCF7953-family logic is naturally compatible with 3.3 V ESP32 GPIO.
- The tool needs an 8 KB or possibly 16 KB EROM image plus an EEPROM image and webserver state.
- An ATmega328P has only 2 KB SRAM.
- An ATmega2560 has 8 KB SRAM, which is still not enough to safely hold a full 8 KB EROM image plus stack, EEPROM data, protocol buffers, and application state.
- The ESP32 can host the web UI and keep all PCF timing local to one MCU.

For a combined AVR + Wi-Fi board, use the ESP32 as the main web/timing controller and communicate with the AVR over UART for unrelated modules. Do not route MDI edge timing through the AVR and then through Wi-Fi.

## Building and opening the web tool

1. Install the **Espressif ESP32 Arduino core** in Arduino IDE.
2. Select the board definition appropriate for the Uno-format WROOM board. `ESP32 Dev Module` is a useful generic starting point when the board vendor does not provide a specific definition.
3. Open `pcf79xxprog.ino`.
4. Optionally enter local Wi-Fi credentials near the top of the file. Leaving `WIFI_SSID` empty is valid.
5. Upload the sketch.
6. Join the access point:
   - SSID: `PCF79xx-Tool`
   - Password: `pcf79xx-tool`
7. Open `http://192.168.4.1/`.

Change the AP password in the sketch before routine use. The interface has no user-account authentication and should only be exposed on a trusted bench network.

The ESP32 always starts its access point. When station credentials are provided, it also attempts to join that network and prints the station IP on the serial monitor at 115200 baud.

## Supported profiles

| Web profile | Init sequence | EROM | EEPROM | Status |
|---|---:|---:|---:|---|
| PCF7945 / PCF7953 / PCF7961 | PCF7945-family | 8192 bytes | 1024 bytes | Main profile |
| 26A0700 legacy | 26A0700 | 8192 bytes | 512 bytes | Based on earlier tool layout |
| 26A0700 experimental | 26A0700 | 16384 bytes | 512 bytes | Unverified; sacrificial target only |

The experimental 16 KB option exists because the later Tusker source declares a 16 KB 26A0700 EROM layout. Its own EROM and MDI buffers remain only about 8 KB, however, so that release can overrun memory when the 16 KB path is used. This ESP32 port allocates a genuine 16 KB EROM buffer, but the target's actual organization and command behavior still require hardware confirmation.

Changing profiles powers the target off and clears both RAM buffers.

## Normal workflow

### Read-only validation

1. Select the profile.
2. Click **Connect**.
3. Click **Read EROM**, then download the EROM buffer.
4. Click **Read EEPROM**, then download the EEPROM buffer.
5. Power-cycle, reconnect, and repeat both reads.
6. Compare the two sets of files before attempting any write.

### Programming an unlocked/erased target

1. Connect normally, or use **Connect + erase/unlock** when the chip is protected.
2. Upload an EEPROM file whose size exactly matches the selected profile.
3. When page-127 bytes must be changed, program EEPROM in **Safe: program special bytes first** mode immediately after erase. This sends `C_PROG_CONFIG` before ordinary EEPROM pages.
4. Verify EEPROM in the same mode.
5. Upload an EROM file whose size exactly matches the profile.
6. Program EROM. Use 64-byte pages for the PCF7945-family profile unless proven otherwise for the target.
7. Verify EROM.
8. Read both memories again and save final backups.
9. Use **Protect / lock** only as the final operation after all verification is complete.

Protecting the device prevents ordinary MDI readout. Unlocking it later requires erase, which destroys programmed memory.

### Protected target behavior

A protected PCF can still enter the early monitor handshake, but the normal `C_TRACE` watchdog-disable confirmation may not appear. The web tool reports that condition as likely protected/locked. Use **Connect + erase/unlock** only when destruction of the existing contents is intended.

## MDI electrical/protocol model

MDI is a target-clocked, two-wire monitor interface:

- **MSCL** is generated by the PCF.
- **MSDA** is bidirectional.
- Each byte is transferred **least-significant bit first**.
- The programmer pulls MSDA low to request the next byte transaction.
- A 500 µs delay is inserted when changing direction between transmit and receive.

### Programmer sending one byte to the PCF

1. Programmer drives MSDA low to request a transfer.
2. PCF raises MSCL.
3. On that first rising edge, the programmer places bit 0 on MSDA.
4. On each following falling edge, the programmer prepares the next bit.
5. After bit 7, the next/final falling edge completes the byte.
6. Programmer drives MSDA high and allows a short recovery time.

### Programmer receiving one byte from the PCF

1. Programmer drives MSDA low to request a transfer.
2. On the first MSCL rising edge, the programmer releases MSDA to input.
3. The programmer samples eight data bits on falling MSCL edges, LSB first.
4. One additional falling pulse terminates the transaction.
5. Programmer drives MSDA high again.

The ISR only changes/samples GPIO and advances a small state machine. Webserver, buffer, and status work stay outside the ISR.

## Monitor-mode entry timing

These values were extracted from `PCF79xx_Tool/Core/Inc/Sysdefines.h` and `Core/Src/mdi.c`.

| Item | Value |
|---|---:|
| Power-off interval before monitor entry | 100 ms |
| PCF7945-family power-on to MSDA high | 500 µs |
| Documented valid PCF7945-family window | approximately 225–725 µs |
| Delay after PCF7945 MSDA high | 200 µs |
| PCF7945 internal-mode low pulse on MSDA | 8 µs |
| 26A0700 delay after MSCL low | 2 µs |
| Delay before requesting ACK | 50 µs |
| Expected monitor ACK | `0x55` |
| MSCL-high timeout during 26A start | 680 µs |
| MSCL-low timeout | 1088 µs |
| Device ACK timeout | 200 ms |
| Complete-byte transaction timeout | 1 s |
| Direction turnaround | 500 µs |
| `C_TRACE` confirmation rise timeout | 400 µs |
| Maximum `C_TRACE` high pulse | 50 µs |
| EROM/EEPROM page-program delay | 5 ms |
| Erase delay before EECON read | 100 ms |

### PCF7945-family entry

```text
Power off, MSDA low, wait 100 ms
MSCL input floating
Power on
wait 500 µs
MSDA high
wait 200 µs
verify MSCL high
wait for MSCL low (<=1088 µs)
MSDA low 8 µs, then high
wait 50 µs
request one receive byte; expect 0x55
```

### 26A0700 entry

```text
Power off, MSDA low, wait 100 ms
MSCL input with pull-down
Power on
wait for MSCL high (<=680 µs)
wait for MSCL low (<=1088 µs)
wait 2 µs
MSDA high
wait 50 µs
request one receive byte; expect 0x55
```

After ACK, a normal connection sends `C_TRACE` (`0x02`), checks the separate MSCL watchdog-disable pulse, and receives two trace bytes. Connect + erase skips `C_TRACE` and immediately performs the erase challenge sequence.

## Important MDI commands

These are PCF monitor commands, not the older five-byte USB wrapper commands.

| Command | Value | Purpose |
|---|---:|---|
| `C_GO` | `0x01` | Run target program |
| `C_TRACE` | `0x02` | Halt/trace and disable watchdog |
| `C_SETDAT` | `0x04` | Write PCF register/data location |
| `C_RESET` | `0x06` | Reset target |
| `C_ER_EROM` | `0x08` | Begin erase/unlock challenge |
| `C_WR_EROM` | `0x09` | Program 32-byte EROM page |
| `C_WR_EEPROM` | `0x0A` | Program 4-byte EEPROM page |
| `C_SIG_ROM` | `0x0C` | Read ROM signature |
| `C_SIG_EROM` | `0x0D` | Read EROM signature |
| `C_EE_DUMP` | `0x0E` | Stream EEPROM dump |
| `C_ER_DUMP` | `0x0F` | Stream EROM dump |
| `C_SIG_EEROM` | `0x11` | Read EEPROM signature |
| `C_PROTECT` | `0x12` | Protect/lock target |
| `C_PROG_CONFIG` | `0x14` | Program special page-127 bytes |
| `C_WR_EROM64` | `0x18` | Program 64-byte EROM page |
| `C_RD_ER_BYTE` | `0x1B` | Read individual EROM byte/range helper |
| `C_SIG_EROM_NORM` | `0x1D` | Normalized EROM signature challenge |
| `C_SIG_XROM_OR_EEROM_NORM` | `0x1E` | XROM or normalized EEPROM signature |

### Erase/unlock sequence

```text
send 08
receive 88
send 55 45 E8 92 D6 B1 62 59 FC 8A C8 F2 D6 E1 4A 35
wait 100 ms
receive EECON
success when (EECON & C0) == 00
```

### EROM page write

```text
send 09 for 32-byte pages, or 18 for 64-byte pages
send one-byte page number
send page data, LSB-first per byte on MDI
wait 5 ms
receive EECON
success when (EECON & C0) == 00
```

### EEPROM page write

```text
send 0A
send one-byte page number
bit-reverse each of the four EEPROM bytes
send the four on-wire bytes
wait 5 ms
receive EECON
success when (EECON & C0) == 00
```

## EROM and EEPROM organization

### EROM

The PCF tool calls program flash **EROM**.

- Main PCF7945/7953/7961 profile: 8192 bytes.
- EROM binary files are stored in normal byte order by this web tool.
- MDI itself sends each byte LSB first; no whole-file bit reversal is applied.
- 32-byte command: `C_WR_EROM` (`0x09`).
- 64-byte command: `C_WR_EROM64` (`0x18`).

The later Tusker comments state that the 64-byte command is required for the complete PCF7945 EROM range. The web UI therefore presents 64-byte mode first for the PCF7945 family.

### EEPROM

The PCF tool calls the nonvolatile data memory **EEROM**; this port labels it **EEPROM** in the web UI.

- Main profile: 1024 bytes.
- 26A0700 profiles: 512 bytes.
- Page size: 4 bytes.
- Downloaded/uploaded files use normal human/tool byte order.
- Every ordinary EEPROM byte is bit-reversed immediately before MDI transmission and reversed after MDI reception.

This bit reversal is essential. It is not applied to EROM.

### PCF7961-style special EEPROM pages

The supplied PCFtool documentation gives this map:

| Page | Byte address | Content | Access |
|---:|---:|---|---|
| 0 | 0–3 | PCF identity, corresponding to transponder identity data | Read-only |
| 126 | 504–507 | Factory trimming information | Read-only |
| 127 byte 0 | 508 | EEDMx/EEDM fields | Read-only |
| 127 byte 1 | 509 | CAL | Read-only |
| 127 byte 2 | 510 | TMODE | Writable through special command |
| 127 byte 3 | 511 | ID/configuration byte | Writable through special command |

The source implementation has a discrepancy: normal safe programming skips pages **0 and 125–127**, while the documentation explicitly describes pages **0, 126, and 127**. The ESP32 safe mode preserves the conservative source behavior:

- skip page 0,
- skip page 125,
- skip page 126,
- program page 127 bytes 2 and 3 with `C_PROG_CONFIG`.

The web UI provides three modes:

- **Safe: program special bytes first** — sends page-127 bytes 2/3 with `C_PROG_CONFIG` before ordinary page writes, then skips pages 0 and 125–127 in the normal loop.
- **Safe: preserve/skip page 127** — skips pages 0 and 125–127 and does not issue `C_PROG_CONFIG`.
- **Manual: skip page 0 only** — mirrors the source's manual path and should only be used when the exact target map is known.

The documentation warns that programming page 127 bytes 2 and 3 only worked under incompletely understood conditions, commonly immediately after erase and before other memory writes. The ESP32 safe mode therefore attempts those two bytes first. Treat the operation as experimental and verify by readback.

## Web functions and API

The embedded page provides:

- device-profile selection,
- connect and connect + erase,
- power off,
- EROM/EEPROM upload to ESP32 RAM,
- EROM/EEPROM target reads,
- binary buffer downloads,
- EROM program in 32- or 64-byte mode,
- safe-special-first, preserve-special, or manual EEPROM program,
- stream verification against the loaded RAM buffer,
- target signatures,
- protect, reset, run, and raw register write.

Useful HTTP endpoints:

| Endpoint | Purpose |
|---|---|
| `/api/status` | JSON state/profile/buffer status |
| `/api/profile?index=0` | Select profile and power off target |
| `/api/connect` | Normal monitor connection |
| `/api/connect?erase=1&confirm=ERASE` | Destructive connect + erase/unlock |
| `/api/poweroff` | Switch target power off |
| `/upload/erom` | Multipart EROM upload |
| `/upload/eeprom` | Multipart EEPROM upload |
| `/api/read?mem=erom` | Read EROM to RAM |
| `/api/read?mem=eeprom` | Read EEPROM to RAM |
| `/api/program?mem=erom&page=64&confirm=PROGRAM` | Program EROM |
| `/api/program?mem=eeprom&mode=safe&confirm=PROGRAM` | Program special bytes first, then safe EEPROM pages |
| `/api/program?mem=eeprom&mode=skip_special&confirm=PROGRAM` | Program EEPROM while preserving special pages |
| `/api/verify?mem=erom` | Verify EROM stream against RAM |
| `/api/verify?mem=eeprom&mode=safe` | Verify writable EEPROM bytes |
| `/download/erom.bin` | Download current EROM RAM buffer |
| `/download/eeprom.bin` | Download current EEPROM RAM buffer |
| `/api/signature?type=erom_norm` | Read selected signature |
| `/api/protect?confirm=PROTECT` | Protect/lock target |
| `/api/register?addr=12&value=34&confirm=WRITE` | Raw `C_SETDAT` register write |

Uploads must exactly match the selected profile size. Buffers are held only in RAM and disappear after ESP32 reset or profile change.

## What was wrong or suspicious in the supplied source

The source archives were compared rather than blindly translated.

### Repository-level warning

The current `PCF79xx_Tool` README states that the project no longer works for multiple users and recommends trying a predecessor. The release history shows a major MDI interrupt-routine rework in v1.3.0 after v1.2.1. That does not prove a single exact failure mechanism, but it makes the earlier transfer ordering a safer porting baseline.

### Definite 16 KB buffer mismatch

The later source sets the 26A0700 EROM size to 16 KB while declaring:

```c
unsigned char erom[8224];
unsigned char buf[8224];
```

A full 16 KB receive/program path therefore exceeds both arrays. The ESP32 version allocates 16384 EROM bytes and does not reuse that array as a small page buffer.

### EEPROM verify compares the wrong array

The supplied `verify_eerom()` contains a comment acknowledging that it compares received EEPROM data to `chip_data.erom[i]` rather than `chip_data.eeprom[i]`. The ESP32 verifier compares against the EEPROM buffer and performs the required per-byte bit reversal.

### Missing `break` after raw register write

In `user_cmd.c`, the `WRITE_PCF_REG` switch case falls through into `VERIFY_ER_BUF`. The web port handles register writes as a separate endpoint.

### Incorrect EROM start-page divisor

Both EROM programming functions calculate the starting page with `EEPROM_PAGE_SIZE` (4) instead of the chosen EROM page size (32 or 64). It is hidden when programming always starts at address zero. The web version currently requires a full image starting at zero and calculates pages directly from their actual EROM page size.

### Fragile EEPROM page-buffer reuse

The supplied EEPROM programmer copies later pages from `mdi.buf` back to the beginning of the same buffer after earlier data has already been overwritten. The ESP32 version keeps a dedicated normalized EEPROM image and constructs a fresh four-byte on-wire page for each write.

### Special-page inconsistency

The documentation says pages 0 and 126 are skipped and page 127 is special. The source also skips page 125. Both behaviors are exposed/documented rather than silently choosing one as universally correct.

## Bench validation plan

### Stage 1 — power only

1. Disconnect MSDA/MSCL from the PCF.
2. Use the web **Power off** and connection actions while monitoring the switched rail.
3. Confirm off voltage approaches 0 V and on voltage is approximately 3.3 V.
4. Check rise/fall time and regulator current.

### Stage 2 — monitor handshake

1. Attach MSDA/MSCL through 1 kΩ resistors.
2. Use a logic analyzer or oscilloscope on target power, MSDA, and MSCL.
3. Attempt Connect on a known readable target.
4. Confirm the monitor ACK decodes as `0x55`.
5. Confirm MSDA contention is not visible at direction changes.

### Stage 3 — repeatable read

1. Read EROM and EEPROM twice with a complete power cycle between reads.
2. Compare binaries byte-for-byte.
3. Use the supplied MATLAB capture extractor as an independent check if a logic capture is available.

### Stage 4 — sacrificial write

1. Use an erased/nonvaluable target.
2. Program EROM, verify, and read back.
3. Program EEPROM safe mode, verify writable bytes, and read back.
4. Inspect pages 0 and 125–127 separately.
5. Test the page-127 special command immediately after erase before relying on automatic order.

### Stage 5 — protection

Only after all previous tests pass, protect the sacrificial target and confirm normal Connect reports the expected locked behavior. Confirm Connect + erase restores monitor access and destroys the programmed contents as expected.

## Known limitations

- Hardware behavior has not yet been verified with the user's exact Uno-format ESP32-WROOM board or PCF targets.
- The 16 KB 26A0700 profile is experimental.
- Special page 127 behavior is target/revision dependent and incompletely documented in the supplied project.
- The web request remains open during long reads/programming operations; the page waits for completion.
- Wi-Fi is kept active during MDI operations. The ISR is short and direct-register based, but scope verification is still important. If timing proves marginal, a later revision can move operations to a dedicated task/core or temporarily use a UART command channel with Wi-Fi paused.
- Buffers are RAM-only; no LittleFS/SD persistence is included in this single-file version.
- There is no TLS or account authentication.
- Full-image upload is required; partial-address programming is intentionally omitted until the page addressing has been validated on hardware.

- a host-side unit test drove simulated MSCL edges through the ISR and confirmed:
